# Contributing to Ramify

Thanks for considering it. This is a small, zero-build, zero-backend project
on purpose (see the Architecture section in `README.md`) - keeping
contributions in that same spirit is the main thing to know before you send
a change.

## Running the tests

```bash
npm ci
npm test           # layer 1: unit tests
npm run test:e2e   # layer 2: end-to-end, real Chrome
npm run build:check # layer 3: deploy safety net (run after npm run build)
npm run test:all   # layers 1 + 2
```

**Layer 1 - unit tests** (`node --test scripts/logic.test.js`, currently
51 tests). Pure logic only: evaluation maths (`public/js/analysis.js`),
pattern detection (`public/js/patterns.js`), the opening book
(`public/js/openings.js`), the weakness profile and spaced repetition
(`public/js/profile.js`), and drill generation (`public/js/puzzles.js`).
None of this loads Stockfish or a browser - the review pipeline takes the
engine as an injected callback specifically so it can be tested this way.
This is the layer to run constantly while you work; it finishes in well
under a second.

**Layer 2 - end-to-end** (`node scripts/smoke.mjs`, currently 25 checks).
Boots the real server, drives a real headless Chrome over the DevTools
protocol (no Selenium/Playwright/Puppeteer dependency - just Node's built-in
`WebSocket`), and walks the actual product loop: engine loads, board
renders, a move is played, a PGN is imported and reviewed, a mistake is
found and tagged, a drill is generated and graded, the profile persists, and
the console stays clean. Run this before anything you touch could plausibly
affect the browser-side app. `npm run test:e2e -- --headful` runs it with a
visible window instead of headless.

**Layer 3 - build check** (`node scripts/build-static.mjs --check`, after
`npm run build`). Verifies the actual deployable artifact in `dist/`: every
import-map target and `href`/`src` resolves to a real file, the Stockfish
and cm-chessboard vendor files are present, and nothing oversized slipped
in. Run this if you touched anything under `public/`, `scripts/build-static.mjs`,
or the vendor mounts in `server.js` - it is the difference between "works on
my machine" and "works on the actual hosted site".

If you only change lesson or opening content (see below), layer 1 is enough
to prove nothing broke; still run layer 2 if you have Chrome available, since
`npm test` does not touch the Learn tab UI at all.

## File ownership / scoping a pull request

This project was built with a strict per-area ownership convention (one
contributor or one agent to a set of files at a time, to keep concurrent
changes from colliding), and the same discipline makes for a much easier
review as an external contributor too. Before opening a PR:

- **Keep it to one area.** A lesson-content PR should touch
  `public/data/lessons-data.js` (and maybe `public/js/lessons.js` if the
  shape genuinely needs to change) - not the engine, the board, or CI.
  An opening-line PR touches the curated `BOOK` array in
  `public/js/openings.js` - not the generated `public/data/openings-data.js`
  (see below).
- **Do not hand-edit generated data.** `public/data/openings-data.js` is
  generated by `scripts/build-eco.mjs` from an external corpus; edit the
  generator or its source data, not the generated file, or your change will
  be silently overwritten the next time it runs.
- **Deploy/CI infrastructure** (`scripts/build-static.mjs`,
  `.github/workflows/*.yml`, `vercel.json`, `wrangler.toml`,
  `functions/api/*`, `api/*`, `lib/coach-prompts.js`, `server.js`) is its own
  area - separate these changes from content or UI changes into their own
  PR so a broken build is easy to bisect.
- Large PRs that cross these boundaries are welcome if the change genuinely
  requires it (for example, a new lesson field needs both the data and the
  renderer) - just say so in the PR description rather than leaving a
  reviewer to guess why unrelated files moved together.

## Code style

- **ASCII only.** No smart quotes, no em dashes, no arrows, no typographic
  symbols, in code, comments, commit messages or PR text. Standard emoji are
  fine in docs; avoid them in code. Check with:
  `LC_ALL=C grep -n '[^ -~]' <file>`
- **ES modules, no build step for `public/js/*.js`.** These files run
  unmodified in the browser (via the import map in `public/index.html`) and
  under `node --test`. Do not introduce a bundler, a transpile step, or any
  syntax that only one of those two environments understands.
- **No new runtime dependencies without a strong reason.** The project has
  exactly three (`chess.js`, `cm-chessboard`, `stockfish`) and no dev
  dependencies at all - testing uses Node's own `--test` runner and a
  hand-written CDP client. Keep it that way unless a change genuinely can't
  be done otherwise.
- Match the existing comment style: a short doc comment at the top of a
  module explaining *why* it exists and any non-obvious design constraint,
  not a comment on every line.

## Proposing a lesson

Lessons live in the `LESSONS` array in `public/data/lessons-data.js`. Each
one looks like this (a real entry, shortened):

```js
{
  id: 'fund-centre-control',        // unique, kebab-case, prefixed by track
  track: 'fundamentals',            // one of: fundamentals, tactics,
                                    // positional, openings, endgames
  title: 'Control the centre before anything else',
  level: 'beginner',                // beginner | intermediate | advanced
  summary: 'One or two sentences: the idea, and why it matters.',
  ideas: ['Two to four concrete, actionable points.'],
  patterns: ['centre-neglect'],     // pattern ids this lesson relates to,
                                    // see PATTERN_LIBRARY in patterns.js
  openings: [],                    // related opening ids, if any
  positions: [{
    fen: '...',                    // a real, legal FEN
    sideToMove: 'b',
    prompt: 'What should the side to move find, and why does it matter here?',
    answer: 'd5',                  // a legal SAN move from that FEN
    explanation: 'Why this move, and what goes wrong without it.',
  }],
  pitfalls: ['Common mistakes a student makes around this idea.'],
  nextIds: ['fund-development'],   // ids of natural follow-up lessons
}
```

Before you open the PR, verify every `fen`/`answer` pair actually loads and
that `answer` is a legal move from it - the fastest way is a few lines of
`chess.js` in a scratch script:

```js
import { Chess } from 'chess.js'
const c = new Chess(fen)
console.log(c.moves().includes(answer)) // must print true
```

A lesson with an illegal or non-existent answer move will fail review
silently for a real student, so this check is not optional.

## Proposing an opening line

The curated plan book is the `BOOK` array near the top of
`public/js/openings.js` - this is what supplies the plan text (`white`,
`black`, `breaks`), not the generated ECO file. An entry looks like:

```js
{ moves: 'e4 e5 Nf3 Nc6 Bb5', eco: 'C60', name: 'Ruy Lopez', struct: 'Spanish',
  white: ['What White is trying to do.'],
  black: ['What Black is trying to do.'],
  breaks: ['The pawn breaks that change the position.'] },
```

- `moves` is a space-separated SAN prefix from the starting position; the
  longest matching prefix in the book wins, so more specific lines should
  generally follow their parent line.
- Use the `eco` code and spelling conventions already in the file (for
  example British spelling, and the shorter of two common names) so the
  book stays consistent.
- `white`/`black` are short plans, not move lists - the whole point of this
  module is explaining the idea behind a structure, not another line to
  memorise.
- If the line is missing from `public/data/openings-data.js` entirely
  (rare, since that corpus is large), that file needs regenerating via
  `scripts/build-eco.mjs` rather than hand-edited - open an issue if you hit
  this rather than editing the generated file directly.
